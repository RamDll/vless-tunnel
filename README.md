# vless-tunnel — прозрачное проксирование всего трафика Ubuntu через VLESS

Один bash-скрипт, который превращает Ubuntu в машину, где **весь трафик** (TCP и UDP,
включая QUIC/HTTP-3) идёт через туннель VLESS на базе Xray-core:

* при первом запуске спрашивает ссылку `vless://` и настраивает всё с нуля;
* при повторном запуске видит, что уже установлено, показывает текущий сервер
  и предлагает **вставить другую ссылку** (пункт меню «Сменить сервер»);
* после установки включение/выключение/смена сервера выполняются **без пароля sudo**
  (пишется точечное правило `/etc/sudoers.d/vless-tunnel`);
* **графическая кнопка**: главное окно — статус и три кнопки, туннель поднимается
  только вручную (автозапуск по умолчанию выключен);
* обязательная поддержка **HTTP** и **QUIC** — см. раздел
  [Поддерживаемые транспорты](#поддерживаемые-транспорты).

---

## Быстрый старт

```bash
# 1) Установка (спросит ссылку vless:// и один раз — пароль sudo)
sudo ./vless-tunnel.sh

# 2) Дальше — без пароля sudo
vless-tunnel on            # включить туннель (с проверкой связи)
vless-tunnel off           # выключить
vless-tunnel toggle        # переключить (то же, что кнопка в GUI)
vless-tunnel status        # состояние
vless-tunnel test          # SOCKS5, HTTP, прозрачный TCP и UDP/DNS
vless-tunnel set-link      # вставить другую ссылку vless://
vless-tunnel gui           # графическое окно
```

Неинтерактивная установка из скриптов/Ansible:

```bash
sudo ./vless-tunnel.sh install --yes \
  --link 'vless://uuid@example.com:443?type=xhttp&security=reality&pbk=...&sni=...&path=%2Fx&mode=stream-one'
```

Установка «ничего не трогая в сети» (служба ставится, но не запускается):

```bash
sudo ./vless-tunnel.sh install --no-start     # потом: vless-tunnel on
```

Удаление (полный откат всего, что сделал скрипт):

```bash
sudo vless-tunnel uninstall                 # убирает всё, включая системного пользователя
sudo vless-tunnel uninstall --keep-config   # оставить конфиг и ядро
sudo vless-tunnel uninstall --keep-user     # оставить пользователя vless
```

То же доступно из меню (пункт 9 при запуске `vless-tunnel` без аргументов) и из GUI
(«Удалить vless-tunnel») — без пароля sudo, с подтверждением, где перечислено, что удалится.

## Автозапуск

По умолчанию туннель **не поднимается при загрузке** — только вручную
(`vless-tunnel on`, `toggle` или кнопка в GUI). Включить автозапуск:

```bash
vless-tunnel autostart on      # включить автозапуск при загрузке
vless-tunnel autostart off     # выключить (туннель сам при этом не гасится)
vless-tunnel autostart         # показать текущее состояние
```

То же можно сделать из GUI («Включить/Выключить автозапуск при загрузке») — без пароля.
При установке автозапуск не включается, если явно не передан `--autostart`.

Watchdog-таймер автозапуск не делает: он лишь восстанавливает правила перехвата,
пока туннель включён (например, после `ufw reload`).

## Графическая кнопка (GUI)

### Запуск

* `vless-tunnel gui` — из терминала;
* ярлык **«VLESS Tunnel»** в меню приложений
  (`/usr/share/applications/vless-tunnel.desktop`);
* пункт 8 в меню терминала (`vless-tunnel` без аргументов).

Окно работает от обычного пользователя, а привилегированные операции выполняет через
`sudo -n` (по правилу NOPASSWD), поэтому пароль не спрашивается. Если запустить от root,
скрипт сам перезапустит окно от имени владельца сессии.

### Главное окно

Сверху — статус:

```
Туннель ВКЛЮЧЁН
Сервер:  95.128.157.141:443  (xhttp / reality)
Ядро:    Xray 26.3.27
Прокси:  socks5 127.0.0.1:10808   http 127.0.0.1:10809
Автозапуск: выключен (только вручную)
```

Снизу — три кнопки:

| Кнопка | Что делает |
|---|---|
| **Включить туннель** / **Выключить туннель** | поднимает или гасит туннель (надпись меняется по состоянию). При включении показывает индикатор, проверяет связь и сообщает внешний IP |
| **Действия…** | открывает выбор остальных действий (см. ниже) |
| **Закрыть** | выход (закрытие окна крестиком делает то же самое) |

### «Действия…»

Диалог с выпадающим списком — выберите пункт и нажмите **«Выполнить»**
(вернуться без действия — **«Назад»**):

| Пункт | Что делает |
|---|---|
| Сменить сервер (вставить новую ссылку) | открывает окно ввода: вставьте `vless://…` — можно вместе с текстом (например, целым сообщением от панели), ссылка будет найдена. Кнопки `Применить` / `Назад` |
| Проверить соединение | SOCKS5, HTTP-прокси, прозрачный TCP, прозрачный UDP/DNS и внешний IP |
| Показать журнал | последние 80 строк журнала Xray |
| Включить / Выключить автозапуск при загрузке | `systemctl enable/disable` для службы. Сам туннель при этом не поднимается и не гасится |
| Обновить ядро Xray | скачивает свежий релиз Xray (для ссылок с legacy-транспортами — зафиксированный `v1.8.24`), сверяет SHA-256, пересобирает и проверяет конфиг, перезапускает туннель. Если новое ядро не пропускает трафик — возвращает прежнее |
| Диагностика | окружение, правила, конфликты с другими туннелями и итоговый вердикт |
| Удалить vless-tunnel | полный откат с подтверждением |

### Окна с текстом

Диагностика, проверка соединения, журнал и результат обновления ядра открываются
в прокручиваемом окне; кнопки — **«Понятно»** и **«Назад»** (возврат в главное окно).

### Что происходит при неудаче

GUI не оставляет машину без связи:

* включение туннеля: если за ~15 секунд трафик через туннель не пошёл — правила
  снимаются, интернет остаётся прямым, в окне появляется причина;
* смена сервера: при неудаче автоматически возвращается прежний рабочий сервер;
* обновление ядра: при неудаче возвращается прежнее ядро; если и оно не поднялось —
  перехват выключается, интернет прямой;
* удаление: если не хватило прав, окно подскажет команду для терминала.

### Особенности реализации

* В GUI намеренно **нет списка-таблицы**: в zenity 4 (GTK4) любому столбцу
  приделывается сортировка, а ключа «отключить сортировку» нет — `--hide-header`
  убирает только текст заголовка. Поэтому главное окно сделано на кнопках,
  а выбор действия — выпадающим списком в форме (`--forms --add-combo`).
* Если в системе старый/урезанный zenity без `--extra-button`, окно не закроется:
  все действия будут доступны одним выпадающим списком.
* Долгие операции показывают индикатор прогресса, результат — отдельным окном.
* Нужен `zenity` (на системах с рабочим столом скрипт доустановит его сам) и
  `python3` для разбора статуса. Трея/иконки в области уведомлений нет — только окно.

## Без пароля sudo

При установке создаётся файл `/etc/sudoers.d/vless-tunnel` вида:

```
имя_пользователя ALL=(root) NOPASSWD: /usr/local/bin/vless-tunnel menu, … on, … off,
    … toggle, … restart, … status, … status --json, … test, … logs, … logs --lines *,
    … set-link, … set-link --stdin, … set-link --link-stdin, … self-update,
    … autostart, … autostart on, … autostart off, … doctor, … update-core,
    … uninstall, … uninstall --yes
```

То есть без пароля разрешены только конкретные подкоманды управления туннелем —
не «любой root». Графическое окно и CLI вызывают их через `sudo -n`, поэтому пароль
не спрашивается.

Кому разрешить — определяется автоматически (`SUDO_USER` при установке) или опцией
`--allow-user user1,user2`. Перезаписать правило: `sudo vless-tunnel sudoers`.
Убрать: `sudo rm /etc/sudoers.d/vless-tunnel`.

Ссылку в режиме «без пароля» GUI/CLI передаёт через stdin (`set-link --link-stdin`),
чтобы в sudoers не попадали аргументы с `:` и `&`.

## Как это работает

```
приложение ──► iptables mangle OUTPUT ──MARK 0x1──► ip rule fwmark 0x1 ──► table 100
                                                        └─ local default dev lo (loopback)
                                                              └─ mangle PREROUTING
                                                                   └─ TPROXY ──► Xray dokodemo-door
                                                                                 (исходный адрес сохранён)
                        └─ DNS (UDP/TCP 53) ──► тот же путь ──► встроенный DNS Xray (DoH через туннель)
                                                          └──► outbound VLESS ──► сервер
```

* **И TCP, и UDP** (в том числе QUIC/HTTP-3) помечаются `MARK 0x1` в `mangle OUTPUT`.
  Дальше `ip rule fwmark 0x1 table 100` + `ip route add local default dev lo table 100`
  заводят пакет на loopback, и там его перехватывает `TPROXY` — только так сохраняется
  исходный адрес назначения.
* Почему **не** `REDIRECT`: если у inbound задан `sockopt.tproxy`, Xray берёт адрес
  назначения из `conn.LocalAddr()`, а `REDIRECT` подменяет его на собственный порт —
  ядро видит это как петлю и рвёт соединение с ошибкой `loopback connection detected`
  (проверено на живом стенде, см. `app/proxyman/inbound/worker.go`).
* Трафик **самого Xray** исключён по владельцу сокета (`-m owner --uid-owner vless`),
  поэтому петли невозможны; служебный пользователь `vless` создаётся автоматически.
  Тем же способом можно исключить свой старый клиент: `--exclude-user xray`.
* **DNS не утекает**: любые запросы на порт 53 (даже на роутер 192.168.x.x и на
  локальный `127.0.0.53`) перехватываются и обслуживаются встроенным DNS Xray —
  обычные домены через DoH-в-туннеле, а домен самого сервера резолвится напрямую
  (bootstrap без петли).
* **Kill switch «по построению»**: если Xray упал, пакеты всё равно уходят на
  локальный порт, где их никто не слушает, — прямого выхода в интернет нет.
* **IPv6**: по умолчанию тоже проксируется; `--block-ipv6` вместо этого блокирует IPv6,
  чтобы не было утечки на v6-адреса.
* Частные сети (LAN, docker-сети, 127.0.0.0/8) по умолчанию идут напрямую;
  `--proxy-lan` заворачивает и их.
* Таймер `vless-tunnel-watchdog.timer` раз в минуту проверяет целостность правил
  (их могут снести `ufw reload`, docker, другие VPN) и восстанавливает их.

Локальные прокси (для приложений, которые не хотят прозрачного перехвата):

| Что | Адрес |
|---|---|
| SOCKS5 (с UDP) | `127.0.0.1:10808` |
| HTTP-прокси | `127.0.0.1:10809` |

Порты меняются опциями `--socks-port` / `--http-port`.

## Поддерживаемые транспорты

Скрипт разбирает ссылку `vless://` и **сам выбирает нужное ядро Xray**:

| `type=` в ссылке | Транспорт | Ядро | Проверено |
|---|---|---|---|
| `tcp` / `raw` | RAW, в т.ч. REALITY и `flow=xtls-rprx-vision` | современное | ✅ e2e |
| `ws` | WebSocket | современное | ✅ конфиг |
| `grpc` | gRPC (+ `mode=multi`) | современное | ✅ конфиг |
| `httpupgrade` | HTTPUpgrade | современное | ✅ e2e |
| **`xhttp`** | XHTTP, в т.ч. **HTTP/2** (`alpn=h2`) и **HTTP/3 = QUIC** (`alpn=h3`) | современное | ✅ H2 e2e, H3-клиент |
| `splithttp` | SplitHTTP (предшественник XHTTP) | современное | ✅ конфиг |
| `kcp` без header/seed | mKCP | современное | ✅ конфиг |
| **`http`** (h2) | legacy HTTP/2 | **legacy `v1.8.24`** | ✅ e2e |
| **`quic`** | legacy QUIC | **legacy `v1.8.24`** | ✅ e2e |
| `kcp` с `headerType`/`seed` | mKCP с маскировкой | **legacy `v1.8.24`** | ✅ конфиг |

Почему два ядра: в новых Xray (≥ v24.9.30 для QUIC и ≥ v24.12.31 для HTTP/2) старые
транспорты `quic` и `http` **удалены** — они «переехали» в XHTTP (`stream-one` H2/H3).
Если ваша ссылка использует `type=quic` или `type=http`, скрипт автоматически поставит
последнее ядро, где они ещё есть (`v1.8.24`), и предупредит об этом. Для всех остальных
ссылок ставится актуальный релиз Xray.

Про **HTTP/3 (XHTTP + `alpn=h3`)**: клиентская часть работает, но собственный
XHTTP-сервер Xray слушает только TCP — H3 терминирует CDN или reverse-proxy
(Cloudflare, nginx, Caddy). Для «голого» сервера Xray используйте `alpn=h2`
(или вообще без `alpn`).

Отдельно про `flow=xtls-rprx-vision`: Xray с этим flow **сам отбрасывает UDP/443**
(«XTLS rejected UDP/443 traffic»), то есть QUIC/HTTP-3 не пошёл бы. Скрипт добавляет
клиентский суффикс `-udp443` (сервер видит обычный `xtls-rprx-vision`) — QUIC работает.
Отключить: `--no-vision-udp443`.

Также поддерживаются: REALITY (`pbk`, `sid`, `spx`, `pqv`), TLS (`sni`, `fp`, `alpn`, `ech`),
`allowInsecure` (в новых ядрах он удалён — скрипт вместо него получает отпечаток
сертификата сервера и прописывает `pinnedPeerCertSha256`), `extra=` для XHTTP (xmux и др.),
IPv6-адрес сервера в `[...]`, ссылки без схемы `vless://` (допишется автоматически),
многострочная вставка (ссылка ищется в тексте, даже если её разорвало переносом строки).

## Совместимость: что будет с уже установленными Xray/sing-box

Коротко: **файлы, бинарники и службы существующих Xray/sing-box скрипт не трогает**
(свои пути, свои имена служб, свой конфиг, никаких вызовов официального установщика
Xray), но **на сетевом уровне два «полных туннеля» на одной машине ужиться не могут**.

| Область | Поведение |
|---|---|
| `/usr/local/bin/xray`, `/usr/local/etc/xray`, `/etc/xray`, `xray.service` | не читает и не изменяет |
| `/etc/sing-box`, `sing-box.service`, бинарник `sing-box` | не читает и не изменяет |
| Свои файлы | `/opt/vless-tunnel`, `/etc/vless-tunnel`, `/usr/local/bin/vless-tunnel`, unit-имена `vless-tunnel*` |
| Системный пользователь | создаёт `vless`; при удалении убирает его, только если он наш (по комментарию в `/etc/passwd`) — чужого не тронет |
| Правила iptables | добавляет только свои цепочки `VLESS_MARK/VLESS_TPROXY`; чужие цепочки не чистит, таблицы целиком не сбрасывает |
| Policy routing | `fwmark` и таблица подбираются свободными (обычно `0x1`/`100`), добавленное записывается в `/run/vless-tunnel/net`; при выключении/удалении снимаются **только свои** записи |
| Порты 10808/10809/12345 | проверяются **до** установки: если занято (например, вашим текущим xray-клиентом) — установка останавливается и предлагает выбрать другие |

Что реально конфликтует:

* **Занятые порты.** Уже слушает локальный прокси на 10808/10809 → поставьте свои:
  `sudo ./vless-tunnel.sh install --socks-port 11808 --http-port 11809`.
* **Существующий прокси-клиент (SOCKS/HTTP без TPROXY).** Прозрачный перехват заберёт
  и его исходящие соединения к его серверу (двойное туннелирование, а при выключенном
  `vless-tunnel` — поломка). Решение: `--exclude-user xray`
  (или `--exclude-user xray,sing-box`) — трафик этих пользователей не перехватывается.
* **sing-box с TUN / WireGuard / OpenVPN с маршрутом по умолчанию.** Это второй «полный
  туннель»: перехват поделить нельзя. Остановите лишнее:
  `sudo systemctl disable --now sing-box` (аналогично `wg-quick@…`, `openvpn@…`).
* **Чужие правила TPROXY/REDIRECT** в iptables/nftables: если они стоят раньше наших
  в `OUTPUT`, перехват достанется им — `vless-tunnel test` покажет, что туннель не работает.

Всё это скрипт проверяет сам: при установке выводит предупреждения и **спрашивает
подтверждение**, а `vless-tunnel doctor` показывает картину целиком.

```bash
vless-tunnel doctor                     # что мешает + вердикт
sudo ./vless-tunnel.sh install --socks-port 11808 --http-port 11809 --exclude-user xray
# либо честно заменить старый туннель:
sudo systemctl disable --now xray && sudo ./vless-tunnel.sh install
```

## Файлы и пути

| Путь | Назначение |
|---|---|
| `/usr/local/bin/vless-tunnel` | сам скрипт |
| `/opt/vless-tunnel/bin/xray-<версия>` | ядра Xray (симлинк `xray`); старое ядро остаётся на диске для отката |
| `/etc/vless-tunnel/config.json` | конфиг Xray (0640 root:vless) |
| `/etc/vless-tunnel/state.json` | состояние: ссылка, порты, ядро (0600 root) |
| `/etc/systemd/system/vless-tunnel.service` | служба |
| `/etc/systemd/system/vless-tunnel-watchdog.{service,timer}` | автовосстановление правил |
| `/etc/sudoers.d/vless-tunnel` | правило NOPASSWD |
| `/run/vless-tunnel/net` | пометка: какие записи policy routing создал скрипт (чтобы не удалить чужие) |
| `/usr/share/applications/vless-tunnel.desktop` | ярлык GUI в меню приложений |
| `/var/log/vless-tunnel/` | логи (если `--access-log`) |

Конфиг-файл всегда проверяется самим ядром (`xray run -test`) **до** перезапуска службы:
если ядро отвергло конфиг, старые `config.json`/`state.json` восстанавливаются.

## Зависимости

`vless-tunnel deps` показывает, что есть, а чего не хватает (отчёт работает и без root);
`sudo vless-tunnel deps --install` доустанавливает недостающие пакеты через `apt`.
То же самое проверяется при установке — установщик сам ставит отсутствующее.

**Обязательные** (проверяются и доустанавливаются автоматически):

| Пакет / утилита | Зачем |
|---|---|
| `curl` | скачивание ядра Xray с GitHub (+ `.dgst` для проверки SHA-256) |
| `unzip` | распаковка архива ядра |
| `python3` | разбор ссылки `vless://`, сборка `config.json`/`state.json`, статус для GUI |
| `iptables` (и `ip6tables`) | правила перехвата: `mangle` MARK/TPROXY |
| `iproute2` (`ip`, `ss`) | policy routing (`ip rule`/`ip route`), проверка занятых портов |
| `systemd` | служба, watchdog-таймер, `journalctl`; без него установка останавливается |

**Для GUI:** `zenity` (на десктопе скрипт доустановит сам), `python3` (уже обязателен),
`runuser` из `util-linux` (сброс окна с root на пользователя).

**Необязательные** — используются, если есть, их отсутствие не мешает:
`visudo` (проверка sudoers), `modprobe` (подгрузить модуль TPROXY заранее),
`nft`/`ufw`/`docker` (расширенная диагностика конфликтов), `systemd-analyze`
(проверка unit-файла), `update-desktop-database` (кэш ярлыков).

**Ядро и права:** модули `xt_TPROXY` + `nf_tproxy_ipv4` (для IPv6 — `nf_tproxy_ipv6`),
root один раз при установке, `CAP_NET_ADMIN` процессу Xray (unit выдаёт
`AmbientCapabilities=CAP_NET_ADMIN`).

**Не требуется:** Go/Node/компиляторы (ядро Xray — готовый бинарник), `openssl`
(отпечаток сертификата снимается средствами Python), docker, СУБД.

## Требования

* Ubuntu 20.04+ (проверялось на 26.04) или Debian с systemd; x86_64 / arm64 / armv7.
* root (или sudo) — один раз при установке.
* Пакеты доустанавливаются автоматически: `curl`, `unzip`, `python3`, `iptables`,
  `iproute2`, при необходимости `zenity` (для GUI).
* Ядро Linux с `xt_TPROXY` (стандарт для Ubuntu; проверяется `vless-tunnel doctor`).

## Диагностика

`vless-tunnel doctor` (кнопка «Диагностика» в GUI) **ничего не меняет** и показывает:

* окружение: ОС, архитектура, systemd, `iptables`/`nft` и их backend;
* поддержку TPROXY ядром (есть ли модуль `xt_TPROXY` — без него не будет прозрачного UDP);
* версию установленного ядра Xray;
* службу: `active/inactive` и автозапуск `enabled/disabled`;
* правила: счётчики наших цепочек в `mangle`, `fwmark`, таблицу, наличие маркера
  «это наши записи», количество `ip rule` с нашим fwmark;
* порты socks/http/tproxy и пометку «УЖЕ ЗАНЯТЫ»;
* конфликты: активные чужие службы (`xray`, `sing-box`, `v2ray`, `mihomo`, `clash`,
  `hysteria`, `openvpn`, `wg-quick`), `tun`/`wg`-интерфейсы, маршрут по умолчанию
  в туннель, чужие правила TPROXY/REDIRECT и чужой policy routing;
* предупреждения по `ufw` и `docker`, DNS-серверы из `/etc/resolv.conf`, маршрут по умолчанию;
* **зависимости** — что есть, чего не хватает (обязательные и необязательные),
  включая наличие модулей `xt_TPROXY`/`nf_tproxy_ipv4`;
* **итоговый вердикт** с рекомендацией:

| Ситуация | Вердикт |
|---|---|
| служба работает, правила и конфиг на месте | `туннель включён, правила и конфиг согласованы` |
| служба работает, а правил нет | `правил перехвата НЕТ — трафик идёт напрямую` → `vless-tunnel ensure` |
| правила остались, ядро не работает | `интернета не будет` → `vless-tunnel off` или `on` |
| выключено | `туннель выключен, правил нет — интернет идёт напрямую` |

Активную связность doctor не проверяет — для этого `vless-tunnel test`
(или кнопка «Проверить соединение» в GUI).

Типовые случаи:

* **не спрашивает пароль sudo** — правило sudoers пишется для пользователя, от которого
  выполнялась установка. Поправить: `sudo vless-tunnel sudoers` (или `--allow-user имя`).
* **`ufw reload`, docker, другой VPN сносят правила** — watchdog восстановит в течение
  минуты, вручную: `vless-tunnel ensure`.
* **прозрачный UDP не работает** (в `test`): проверьте, что модуль `xt_TPROXY`
  загружается и ядро службы запущено с `CAP_NET_ADMIN`
  (`systemctl show vless-tunnel -p AmbientCapabilities`).
* **сайт не открывается, а `test` проходит** — домен может не резолвиться через
  DoH-в-туннеле; добавьте DNS напрямую: `--direct-dns 1.1.1.1,8.8.8.8` (или свой резолвер).
* **не скачивается ядро** — используйте зеркало `--gh-proxy https://ghproxy.net/`
  или локальный файл: `--from-file /path/to/xray`.
* **нужно вернуть прямой интернет** — `vless-tunnel off` (правила снимаются автоматически).

## Что проверено

Основной способ проверки — контейнерный стенд `tests/container-test.sh`: он поднимает
Ubuntu в Docker **со своим network namespace** (только `CAP_NET_ADMIN`, без
`--net=host` и `--privileged`), поэтому правила и маршруты применяются внутри
контейнера и **хост не затрагивается**. Стенд состоит из 23 шагов и 28 проверок
(контейнер → зависимости → локальный VLESS-сервер и клиент → проверки) и включает:

* **зависимости**: на чистом образе `deps` видит отсутствие `curl`/`python3`/`iptables`
  и возвращает ошибку, а `deps --install` доустанавливает пакеты (и честно сообщает
  про отсутствие systemd в контейнере);
* сборку конфига генератором скрипта и его проверку ядром;
* запуск клиента под пользователем `vless` с ambient `CAP_NET_ADMIN` — как это делает
  systemd на хосте;
* контроль «до правил» (трафик идёт **мимо** туннеля);
* `_tproxy up` → прозрачный TCP и прозрачный UDP/DNS идут через туннель;
* локальные прокси SOCKS5 и HTTP;
* идемпотентность (повторный `up` не плодит правила);
* kill-switch (при погашенном ядре трафик не утекает напрямую);
* `_tproxy down` и восстановление связи;
* фолбэк ядра при недоступном GitHub;
* автоотключение перехвата, если туннель не отвечает (`on`);
* `install --no-start` (правила не применяются, интернет прямой);
* незавершённую установку без unit-файла;
* многострочную вставку ссылки (и через pty, как из терминала, и через `--link-stdin`);
* автозапуск: по умолчанию не включается, `--autostart` включает, `autostart off` снимает;
* все команды, которые вызывает GUI (проверка, что парсер их принимает);
* GUI-поток с заглушкой zenity (кнопки → «Действия…» → выпадающий список → окно с текстом);
* полный откат: `uninstall` убирает службу, таймеры, правила, конфиг, ядро, логи,
  ярлык и системного пользователя, а связь остаётся.

Дополнительно проверялось:

* валидация ядром конфигов для 16+ вариантов ссылок (tcp/reality/vision, ws, grpc,
  httpupgrade, xhttp+reality, xhttp+h3, xhttp+`extra`, splithttp, kcp, legacy http,
  legacy quic, IPv6-сервер, self-signed с `pinnedPeerCertSha256` и др.);
* сквозные тесты в изолированной песочнице: VLESS+TCP+TLS, legacy HTTP/2, legacy QUIC,
  HTTPUpgrade, XHTTP+H3 (клиент), SOCKS5, HTTP-прокси, резолв DNS через туннель;
* живой прогон на Ubuntu 26.04 с реальным сервером (REALITY + XHTTP + vision + VLESS
  encryption): прозрачный TCP и UDP, SOCKS5/HTTP, переключение без пароля, autostart;
* подбор свободных `fwmark`/таблицы, пометка своих записей policy routing
  (чужое не удаляется), защита от удаления чужого пользователя `vless`.

## Ограничения

* Проксируется только сама машина (не шлюз для других устройств в LAN);
  трафик docker-контейнеров идёт через `FORWARD` и в туннель не попадает.
* Смену ссылки между legacy (`quic`/`http`) и остальными транспортами скрипт делает
  автоматически (перекачивает нужное ядро), но одновременно два транспорта
  из разных «эпох» Xray одним ядром не поддержать — это ограничение Xray.
* `pinnedPeerCertSha256` фиксирует конкретный сертификат: если сервер сменит
  самоподписанный сертификат, повторите `vless-tunnel set-link` с той же ссылкой.
* `update-core` для ссылок с legacy-транспортами не «обновляет» ядро — версия
  `v1.8.24` зафиксирована (в новых Xray этих транспортов нет), команда просто
  переустанавливает её. Старые бинарники ядер в `/opt/vless-tunnel/bin` не удаляются.
* GUI — окно (zenity), без трея и уведомлений; на серверах без графики доступен
  только CLI и меню в терминале.
